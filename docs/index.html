Know why every widget rebuilt.

Flutter DevTools tells you what rebuilt. why_rebuild tells you why, whether the work was wasted, and how to fix it. Your AI coding agent can ask it too.

It's a debug-only package. Add one line to main(). No wrapper widgets, no setup screens, and nothing ships in your release build.

Add it from GitHub until it's on pub.dev:

dev_dependencies:
  why_rebuild:
    git: https://github.com/flutterboy20/why_rebuild
void main() {
  WidgetsFlutterBinding.ensureInitialized();
  WhyRebuild.instance.install();
  runApp(const MyApp());
}

    The problem it solves

    Every time something changes on screen, Flutter runs build() again for the widgets involved. That's normal. The trouble starts when Flutter rebuilds widgets whose content didn't change at all. Each extra rebuild costs a little time, and on a busy screen those costs add up to dropped frames: the app stutters when you scroll, type or animate.

    DevTools can count rebuilds, but a count doesn't tell you who asked for the rebuild, or whether it was needed. So people guess, sprinkle const around, and hope.

    It's like repainting the whole house because one light bulb was changed. why_rebuild shows you who ordered the repaint, and which rooms didn't need it.

    Three mistakes it catches in seconds

    State kept too high up

    A page calls setState to update a cart count, so every product tile on the page rebuilds too.

    Fix: move the count into a small widget of its own, or make the tiles const.

    Reading all of MediaQuery

    A form uses MediaQuery.of(context) to get the screen size, so it rebuilds every time the keyboard moves.

    Fix: use MediaQuery.sizeOf(context).

    Animations that rebuild everything

    An AnimatedBuilder rebuilds its whole chart 60 times a second, even though only a spinner moves.

    Fix: build the chart once and pass it as child.

    How it works

    Flutter has a debug-only hook that runs whenever a widget is marked to rebuild. why_rebuild listens on that hook and, for each of your widgets, works through five steps.

    1. Notice the rebuild

      A widget in your app is marked "needs rebuild".

    2. Find who asked

      It records the call stack, so it knows the exact method and file:line that started it.

    3. Name the cause

      setState, a changed InheritedWidget, an animation, a state library, or a parent rebuilding.

    4. Check if it was wasted

      It compares the widget's properties before and after. Same properties means wasted work.

    5. Suggest a fix

      It matches the pattern to a known fix, like "make it const" or "use MediaQuery.sizeOf".

    The answer is available in three places:

    Your Dart codewhy('ProductTile'), report(), wasted()
    Your AI agentthrough the official Dart MCP server, no extra server
    Your testsexpectRebuildBudget fails the test and prints the fix

    Three ways to use it

    Ask from Dart

    Handy while you're debugging one screen. Print the top offenders or ask about one widget by name.

    final scan = WhyRebuild.instance;
print(scan.report(limit: 5));
print(scan.why('ProductTile'));
print(scan.wasted());
scan.reset();

    Let your AI agent ask

    Claude Code, Cursor and others connect through dart mcp-server, which ships with the Dart SDK. The agent records, reproduces the slow flow, reads the causes, edits the code and checks again. The repo includes a ready-made skill file for this.

    ext.why_rebuild.record  action=start
  ...use the app...
ext.why_rebuild.record  action=stop
ext.why_rebuild.why     widget=ProductTile

    Guard it in tests

    Once a screen is fast, keep it fast. The test fails if a tap creates wasted rebuilds, and the failure message tells you why.

    scanTest('add to cart stays cheap',
    (tester) async {
  await tester.pumpWidget(const MyApp());
  await expectRebuildBudget(tester,
      () => tester.tap(find.text('Add')),
      forbidWasted: ['ProductTile']);
});

    How it helps the team

    • Less guessing. Every rebuild comes with a reason and a file:line. You fix the line it points to instead of trying things.
    • Agents can do the legwork. An AI agent can find, fix and verify wasted rebuilds on its own, then show before and after numbers.
    • Reviews get concrete. "This adds 40 wasted rebuilds per tap" is easier to act on than "this feels slow".
    • Regressions get caught. Rebuild budgets in tests stop a fast screen from quietly getting slow again.
    • It works with your state library. provider, Riverpod, Bloc, GetX, MobX, signals and flutter_hooks are recognized without any extra setup.

    For interns: your first 20 minutes

    1. Add the package and the one line

      Put the dependency in pubspec.yaml and call WhyRebuild.instance.install() in main(), right after ensureInitialized().

    2. Run the app in debug mode

      Use flutter run on an Android or iOS device, simulator or desktop. It doesn't work on web yet.

    3. Use the screen that feels slow

      Tap, scroll or type through it a few times, just like a user would.

    4. Ask what was wasted

      From a debug button or a test, print the list of widgets with wasted rebuilds:

      print(WhyRebuild.instance.wasted());

    5. Read the fix hint and apply it

      Open the file:line it gives you. Most fixes are small: add const, split a widget, pass a child, or read less from MediaQuery.

    6. Prove it worked

      Hot reload, call WhyRebuild.instance.reset(), repeat the same taps and check again. The wasted count should drop to zero. Then add a scanTest so it stays that way.

    Reading an answer

    {"widget": "ProductTile",
 "location": "lib/main.dart:173",
 "rebuilds": 15, "wasted": 15,
 "causes": {"parent rebuilt (HomePage)": 15},
 "triggers": {
   "setState in HomePageState.addToCart
    at lib/main.dart:164": 15},
 "fixHint": "Rebuilt only because an ancestor
   rebuilt; its props never changed. Make it
   const, or move the state that changes into
   a smaller widget."}
    1. location is where your code creates the widget. That's the line to edit.
    2. rebuilds and wasted: here all 15 rebuilds were wasted. That's pure waste, so start with this one.
    3. causes says why: its parent HomePage rebuilt and created it again.
    4. triggers goes one step further back, to the code that started it all: addToCart calling setState.
    5. fixHint tells you what to change. If it's empty, the rebuild was needed and you can leave it alone.

    It never breaks your app

    Debug builds onlyIn profile and release builds the scanner is removed completely, so users never run it.
    Steps aside for DevToolsTurn on "Count widget builds" in DevTools and why_rebuild pauses by itself, then comes back when you turn it off.
    Protects itselfEvery hook is wrapped in error handling. After repeated internal errors it switches itself off instead of crashing your app.
    Quiet by defaultNo console spam, and your own logs pass through untouched. Each problem is reported once.
    Small overheadAbout 1.1–1.5 times normal debug build time while recording, measured on the example app.
    Plays fair with other toolsIf another tool already uses the same Flutter hook, why_rebuild leaves it alone and tells you.
    Flutter3.27 and newer, tested in CI on 3.27, 3.47 and 3.50
    Android, iOSSupported in debug mode
    Windows, macOS, LinuxWorks (same engine)
    WebNot yet: install() prints one warning and does nothing
